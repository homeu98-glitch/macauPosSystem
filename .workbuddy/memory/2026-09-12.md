## 第二輪：付款狀態閃爍 + 「取消結帳」補回（同日 · 用戶需求 2 點）

**用戶報告**：① 訂單明明已結帳，入到線下訂單頁「已結帳」**閃一下又彈返「未結帳」**；

### 閃爍根因（三條路，全部要守）

1. **客戶端合併用錯鐘域**（主因）：`mergeOrderLists()` 以前用 `orderTimestamp()`
   ＝`updatedAt`。但本機寫入嘅 `updatedAt` 係 **iPad 鐘**；雲端返嚟（`/api/pos/state`
   backfill、realtime push）嘅 `updatedAt` 係 `mapOrderRow()`/`mapPosOrderRow()` 映射嘅
   **`pos_orders.updated_at` = server 蓋章**。而 server 端 LWW 一直用 `client_updated_at`
   （client 鐘）→ 兩邊唔同尺，舊狀態 snapshot 只要 server 收件時間較新就「扮新」贏出。
2. **`paid` 冇守門**：快餐 counter 結帳寫 `paid`（唔係 terminal 嘅 `settled`，要等「完成」），
   所以 `TERMINAL_ORDER_STATUSES` 同「終態優先」都擋唔到佢被 `draft`/`sent_to_kitchen` 降級。
3. **收銀台「下單」會把已收款單打返 `sent_to_kitchen`**：流程 落單 → 結帳(paid) →
   喺 strip 撳返張卡載入點餐頁 → 再撳「下單」。`resolveExistingOrderForUpsert()` 嘅
   `activeOrderId` 分支會回饋嗰張 paid 單，`upsertCurrentOrder()` 就寫 `sent_to_kitchen`。

### 🔑 稱重：唔需要藍牙 —— 用「條碼標籤秤」（本次最重要發現）

- 🔴 **Web Bluetooth / Web Serial / WebHID 在 iPad 上全部行唔通**：Apple 由 App Store 規則強制
  **所有 iOS／iPadOS 瀏覽器用 WebKit 內核** → 連 iOS 版 Chrome／Edge 都冇 Web Bluetooth。
  「靠瀏覽器直接連藍牙」呢條路在 iPad 上**永遠不成立**（除非裝 Bluefy / WebBLE 第三方瀏覽器）。
- ✅ **業界標準做法（首選 W1）＝ 條碼標籤秤 / price-embedded EAN-13**：秤自己印一張不乾膠標籤，
  條碼內容就係 PLU + 重量或金額，**POS 只當普通條碼掃 → 零整合、零驅動、iPad 直接可用**。
- 條碼結構：`2` 或 `02`（前綴 20-29 = 店內變重碼，21=重量碼、22=金額碼）
  ＋ 5 位 PLU ＋ 5 位重量(克)或金額(分) ＋ 校驗位。
  ⚠️ **各品牌出廠規則唔同**（前綴 `2` vs `02`、克 vs 千克、有冇校驗位、位數分配）→ 必須可配置。
  常見品牌：大華、頂尖、寺岡 DIGI、CAS、Mettler-Toledo。
- W2 = 經 **Companion 代理**做藍牙秤（新增 `/api/scale`，Node 進程做 BLE，瀏覽器只問 companion
  → **完全繞開 Safari 限制**）；但每個秤型號要適配 GATT UUID，成本高一個量級 → Phase 3。
  ✅ 架構先例已存在：`companion.ts:553`（`/api/usb`）、`:583`（`/api/printers`）、
  `:628`（`/api/bluetooth`）、`:532`（`/api/discover`）。
- W3 = USB HID 秤（模擬鍵盤，零驅動，有線）；W4 = 手動輸入（**永遠保留，唔可以省**）。
- ⚠️ W1 配套：秤端商品庫同 POS 要用**同一套 PLU**、禁止秤端隨意改價，否則「秤上價 ≠ POS 價」。

### 🔑 新增細節：秤標籤「金額碼」反推重量
