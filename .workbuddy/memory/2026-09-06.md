## 修正：pos_queue_events 驗證 dump（original_store 全 null）
用戶跑咗我建議嘅 `payload->'order'->>'storeId'` 驗證 SQL，結果全部 null。核查代碼後確認：
- **唔係 SQL 跑錯，係 queue payload 根本唔帶 storeId**：
  - ORDER_CREATED：`pos-app.tsx:2465` `payload: order`（冇 `.order` 包裝）→ `payload->'order'` null。
  - ORDER_UPDATED：`payload: { order, addedItems }`，但 `order` 物件（`/api/pos/sync` route.ts:228-258 解析欄位）冇 `storeId/store_id` 欄 → 依然 null。
- **pos_queue_events 表 upsert（route.ts:200-210）冇寫 store_id** → 全表零店鋪隔離，呢點同 `pos-app.tsx:771` 註釋（「pos_queue_events 無 store_id，server 列表含其他店」）互相印證。
- **結論修正**：跨店串號唔係「帶錯店被 re-stamp」，而係 queue 事件壓根無 store 資訊，`pos_orders.store_id` 100% 由 flush 當刻 `resolveStoreId()`（當前登入 merchant，sync-flush.ts:221-227,261）+ `upsert onConflict id` 全行覆寫（route.ts:229,260-261）決定。
- **我之前建議嗰句「對比 payload 原 storeId」SQL 係錯嘅**：payload 冇 storeId 搵極都 null，冇法用嚟搵 re-stamp 單。正確驗證改為直接對 `pos_orders.store_id` 同外部真源（online_order_id→ledger 渠道 / local_order_no 歸屬），或沿用截圖 vs CSV 嘅 dishes 聚合吻合證明。
- 份 dump 係 `pos_queue_events` 全表（order-*/kiosk-*/print-* 混合），佐證 queue 全店混入。Local vs Online 差異結論不變。

- `docs/pos-cross-store-isolation-fix-plan.md`（方案文檔，已標記實施狀態）。

**核心改動**：

- `sync-flush.ts`：新增 `withStoreScope()`（只 stamp 新事件，已有 storeId 唔覆寫——鐵律：只可以餵新建事件，唔好成條 queue 過，否則 legacy/外店 undefined 事件會被改姓）+ `filterEventsForCurrentStore()`（flush 閘口：只放行 `storeId === resolveStoreId()`，undefined 一律唔推）；`doFlush` legacy-heal 後套過濾 + body 每事件帶 `storeId`。
- 入隊入口 ×7 全部 stamp：pos-app `pushEvents`（`[...queue, ...withStoreScope(events)]`）、print-center `pushEvents`、pos-orders confirm/rejectSelfOrder、quick-order-fulfillment `persistOrderUpdate`、shift-page 兩處 PRINT_JOB 事件、print-jobs `deletePrintJobsOnServer`（用請求同一 storeId）、kiosk-order `submitKioskOrder`（用參數 storeId 即 kiosk 綁定店）。
- **三條獨立 flush 路徑全部加閘**（實施時新發現，原方案漏咗）：shift-page `forceSyncBeforeClose`（retryable 套 filter）、shift-page `closeShift` POST（scoped + 只標 scoped 為 synced）、pos-app `syncNow`（scoped + `persistQueue` 只標 scoped，外店事件保留原狀）。

- `storage.ts` `legacyDataBelongsToMerchant`：冇 legacy bootstrap 標記由返 true 改返 **false**（無法證明歸屬就唔遷移，數據留 legacy key）。
