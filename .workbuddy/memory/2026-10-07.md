### 🔴 核心不變量（守衛測試守住）
1. **永不覆寫**：`baselinePatch` 只喺 `hit.baseline_unit_cost === null` 時先有值。
   ⚠️ 唔可以因為「搵到更早日期」就改寫 —— 舊收據可能被刪／補登，令**已報告咗嘅上漲金額自己郁**。
2. **duplicate-key 補插路徑**（`ilike`）用 `hasBase` 守住，唔可以漏。
3. **冇基準 ⇒ `changeAmount: null`（唔係 0）**，`direction: "new"`，`isComparable("new") === false`。
   當 0 會令「漲價影響金額」合計細咗、睇落好似真係零影響。
4. **基準 ≤ 0 或 null ⇒ 當 new**，唔會出 `Infinity`／`NaN`。
5. **漲／跌金額分開加**（`totalUpAmount` / `totalDownAmount`），唔可以淨計 `Σ(changeAmount)`
   —— 咁漲跌互相抵消，睇唔出真實影響。
6. `unit_price <= 0` 唔做基準。
7. 同日多筆 → 揀**單價較低**者（保守，令漲幅偏細，唔會誇大呃老闆加價）。

## 清零既有 4 個 fail（2026-10-07 深夜 · J 指示「4 個既有 fail 修掉再一起上」）

### 🔴🔴 真 bug：duplicate-key 補插路徑靜默清空商家資料

**位置**：`src/lib/inventory-products.ts` 嘅 `duplicate key|unique constraint` 分支。

原本只 `select("id, baseline_unit_cost")`，然後直接寫
`last_purchase_date: row.last_date` / `last_supplier: row.last_supplier` / `category: row.category`
—— **冇**主路徑嗰個 `?? 現有值` 降級。而 `row.*` 可以係 `null`
（今次掃到嘅收據冇日期／供應商／品類）。
⇒ 走 duplicate-key 補插（併發／撞名）時，會把商家填好嘅供應商／品類**靜默清空成 null**。

**為何一直冇發現**：主路徑（`hit` 存在）行為正確；duplicate-key 只在併發／撞名才走。
呢個正是 P2 文件自己寫過嘅警語（「兩行一定要同 update payload 對齊」）嘅漏網之魚。

✅ **修法**：select 補齊 `last_purchase_date, last_supplier, category`，並用
`row.x ?? dupRows?.x ?? null` 逐欄降級（同主路徑逐字一致）。
✅ **回歸守衛已驗證有效**：暫時還原舊寫法 ⇒ 守衛即刻報錯。

### 測試寫得太死（守「代碼字串」而非「行為」）— 4 條

| 測試 | 壞喺邊 |
|---|---|
| `onMutated` | 斷言「**剛好 4 個**」，但 `runSync` 嘅 `silent ?: ` 兩分支各要 notify ⇒ 實際 5 個 |
| `duplicate-key…（用 hasBase）` | 斷言字串 `/hasBase/`，實作已改用 `shouldWriteBaseline()` |
| `syncFromReceipts 只喺 baseline NULL 時寫入` | 斷言逐字 `hit.baseline_unit_cost !== null`，實作已變 `shouldWriteBaseline(hit?.…)`；`const baselinePatch =` 實際有型別標註 |
| `一鍵同步要打同一支 sync API` | 斷言整句 `body: JSON.stringify({ store: merchantId, account })`，P2 加咗 `mode` 就爆（但契約冇壞） |

**⭐ 通則（已入坑）**：守衛測試要守「**行為不變量**」（缺咗會出咩事），
唔係「某一行代碼長點樣」。寫死一整句代碼 ⇒ 任何無害重構都爆，
而**真正壞掉時反而可能唔爆**。

### ⭐ 新工具：`functionBody(src, fnName)`（守衛測試用）

抽函式體。**唔可以「搵第一個 `{`」** —— 參數本身可能係 destructure／型別字面量：
`const runSync = useCallback(async ({ mode, silent }: { mode: "auto" | "manual"; silent: boolean }) => {`
⇒ 第一個 `{` 命中 `{ mode, silent }`。

✅ **策略**：由宣告處往後逐個 `{` 試配對（跳過字串／模板），**取內容最長者**
（參數／型別一定短過函式體），搵到 >100 字候選就收工。

🔴 **兩個坑**：
1. 本專案檔案係 **CRLF** ⇒ `stripComments()` 用 `^[ \t]*//.*$` 多行模式對唔上 `\r\n`，
   要**先 `replace(/\r\n/g,"\n")`**。
2. 唔可以用「>40 字就算函式體」嘅門檻 —— `{ mode, silent }: { mode: "auto" | "manual"; silent: boolean }`
   本身就 **44 字**，會誤中參數。

## 🔴🔴 門店層設定（品類／單位）冇同步到雲端 —— 三個病灶全修（J 實案）

**症狀**：喺另一台電腦新增品類，本機／其他裝置永遠睇唔到（庫存 → 設置 → 品類顯示「0 個」），
但**成功提示照出**（`await onSaveCategories(...)` 唔會拋錯），所以商家以為「已保存」。
供應商冇事（走 expenseRecorder `merchants` 表），呢個落差令問題極難察覺。

### 病灶 1：`patchLocalSettings()` 只寫 localStorage，從來冇推雲
`inventory-view.tsx` 嘅 `saveCategories`／`saveUnits`／`saveSupplierOrder`／`saveCategoryOrder`
／`saveUnitOrder` 全部經 `patchLocalSettings()`，而佢只有 `savePosLocalSettings(merged)`。
**全個 repo 冇任何一行**把 `invCategories` 推上雲 ⇒ 品類係「本機私有」。
✅ 修：寫完本機即刻 `POST /api/pos/device-config`。三個必要細節：
- 帶 `posDeviceAuthHeadersFresh()`（該端點有鑑權閘，`POS_REQUIRE_DEVICE_AUTH` 冇設＝開閘但仍要憑證）。
- **推前 `stripReopenTempTables(merged.floors)`** —— 唔剝會令返結暫存枱永久升級做真實枱
  （`table-scope.ts` 鐵律表）。`device-settings` 兩處推雲都做咗。
- body 係 `{ ...deviceConfig, storeId, updatedAt, localSettings }`：
  該端點係 `upsert(..., { onConflict: "device_id" })`，**只送 `{storeId, localSettings}` 會令 `device_id` 變 null 而炸**。
- 失敗只 `console.warn`，**唔 rollback、唔 throw**（本機已寫入＝資料唔會丟）。

### 病灶 2：`device-settings.tsx` 拉雲端嘅閘係**死條件**
原本 `const needLocalSettings = !cachedLocalSettings;`，但
`loadPosLocalSettings()` **永遠**回 normalized 物件（key 唔存在就回 `defaultPosLocalSettings`）
⇒ `!cachedLocalSettings` **恆為 false** ⇒ `if (needLocalSettings && payload.localSettings)` 永不執行
⇒ 從來唔會採用雲端 `local_settings`。
`storage.ts` 本來就有 `hasPosLocalSettings()`（raw key 探測）專為分辨呢件事而寫，但冇用到。
✅ 改用 `!hasPosLocalSettings()`；補 default 嘅 guard（原本 `&& !loadPosLocalSettings()` 亦係死條件）同步改用。
🔴 Guard **唔可以**改用 `adoptedFromDb` flag：若雲端只有 deviceConfig、`localSettings` 係 null，
就補唔到 default ⇒ `needLocalSettings` 永遠 true ⇒ **每次 render 重複打 API**。

### 病灶 3：上面嗰個閘只覆蓋「全新裝置」
`!hasPosLocalSettings()` 對「用過嘅第二台機」永遠 false ⇒ 推咗上雲都照樣顯示 0 個。
✅ 庫存頁加一次性雲端補值 effect：
- **逐欄「只補空」**（本地 `length === 0` 且雲端非空才補）⇒ **絕不可能**令商家已見到嘅資料消失。
- **本地齊全時完全唔發請求** ⇒ 正常裝置零額外 egress（唔會為修一個 bug 而增加日常流量）。
- 用 `useRef` 一次性 guard（StrictMode 開發模式會行兩次）。
- 刻意**唔經** `patchLocalSettings()`，亦唔回寫雲端 ⇒ 避免兩台機互推。
- 失敗（離線／401）靜默保持本機值。
