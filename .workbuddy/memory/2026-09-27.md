### 病根（🔴 唔可以再犯）
`subscribe()` 開頭自己 `removeChannel(舊 channel)`，而 supabase-js 會對**舊 channel** 嘅
subscribe callback 送 `CLOSED`；四個 hook 都把 `CLOSED` 當「斷線要重連」⇒ 死循環：
回前景 → 移除舊 channel → 收 `CLOSED` → 排 3 秒重連 → 又移除**剛建好嘅健康 channel**
→ 又 `CLOSED` → 無限循環。每圈 `SUBSCRIBED` 後 3 秒 debounce 觸發 `onResubscribed`
→ 又一次增量 `list_merchant_orders`。**只要畫面回前景一次，就會一直循環到關頁。**

### 🔴 關鍵教訓：`use-pos-realtime` / `use-kds-realtime` 本身已經用「先清空變數再 await」都唔夠
呢兩個 hook 2026-09-15 已改成 `const stale = channel; channel = null; await removeChannel(stale)`。
**但依然中招** —— 因為 callback 入面**冇分辨「呢條 callback 屬於邊條 channel」**，
舊 channel 回嘅 `CLOSED` 一樣會排重連。⇒ 「清空變數」只解決咗**洩漏**，
冇解決**回授**。根治一定要 callback 自比：`if (cancelled || channel !== ch) return;`。

### 修法（四檔一致，逐檔對稱）
```ts
const ch = supabase.channel(`<topic>`).on(...)....;
channel = ch;
ch.subscribe((status) => {
  if (cancelled || channel !== ch) return; // 舊 channel 被自己移除 → 忽略
  // SUBSCRIBED / CHANNEL_ERROR / TIMED_OUT / CLOSED 原邏輯（CLOSED 唔可以刪！）
});
```

## Ledger 線下報表：時間判斷同 filter 邏輯（J 提問 → 拍板「維持三欄」）

### J 嘅疑問同正確答案（要記住，將來會再問）
1. 「冇時間資訊，唔就判斷唔到係唔係今日？」→ **啱一半**：真係睇唔到逐張單嘅日期，但**唔需要**
   判斷 —— 歸屬由**呼叫者傳入嘅 `from`/`to`** 決定。
2. 「套 filter 會唔會全部錯亂？」→ **唔會**：filter **從來唔喺 Ledger 側執行**。
   換區間 ＝ **重新叫一次 API**（契約 §成本與行為：進報表 Tab／換區間各一次）。客戶端永遠只有
   「已篩好嘅一批」，本地冇機會篩錯。三節（`kpi`／`orders[]`／`dishes[]`）共用**逐字相同**嘅 where。
3. 「呼叫時就已經知道範圍？」→ **完全正確**，而且回應 echo `from`/`to`/`clamped` 畀對方核對。

### 真正嘅限制（已寫入增補契約專節）
**跨日區間嘅回應冇內部粒度** ⇒ Ledger 唔可以本地 group by day、唔可以加「日期」欄。
要「某一日」⇒ `from = to = 該日` 另叫；要逐日趨勢 ⇒ 逐日各叫（POS 限流每店每分鐘 30 次）。
（呢個係契約刻意設計：session cache、唔 polling。）

### 拍板
**維持三欄**（`orderNo` / `totalAvos` / `status`），**唔加**時間欄位。

### 🔴 若日後要加時間：正確設計（唔好臨場亂揀）
* 一定要用 **SQL 篩選用嘅同一個 event instant**（`coalesce(settled_at, reopened_at, updated_at, created_at)`），
  唔可以另回 `created_at` —— 否則出現「顯示 09-25、被算入 09-24」嘅鬼故事。
* 只回 `at`（RFC3339 `+08:00`）**唔夠**：對方用 UTC 切片 ⇒ 00:00–08:00 嘅單歸錯日。
  ⇒ 一定要連 **`day`（`YYYY-MM-DD`，澳門日）** 一齊回，由 POS 講明「我當佢係邊一日」。
  成本 ≈ +40 KB / 90 日（實測 2 900 張單）。additive，`v` 唔升，caps 加項。

### 一個 edge case（已寫入文件）
`orders[]` 包未結帳單，而 `draft`/`sent_to_kitchen`/`reopened` 冇 `settled_at`／`reopened_at`
⇒ 日歸屬落到 **`updated_at`**（server 蓋章）。所以進行中嘅枱會一直出現喺最近區間（合理），
久未觸碰嘅草稿會停喺最後動作嗰日。（已收錢嘅單有 `settled_at` 錨住，唔受重推影響。）
