# 2026-09-30

## 🔴 admin「店鋪總覽」今日單數 21 ≠「營業報表」訂單數 20 —— 已定位（澳覓 created_at 時區偏移）

**症狀**：admin dashboard 表嫂美食顯示「今日 21 單 / MOP 1,407.00」，點入營業報表變「20 單 / MOP 1,294.00」。

**取證**（`tools/_probe-reportsplit-20260930.cjs` ＋ `_probe-reportsplit2-20260930.cjs`，anon 直讀生產 `pos_orders`）：
同一批 51 張雲端 row 跑兩個 predicate，**精確復現** 21 / 1,407 與 20 / 1,294。
差集只有 **1 張**：`澳覓#2` MOP 113，`ext=TK001280260929194659140`。
- `created_at` = 澳門 **09-30 03:47:07** → 總覽算今日
- `settled_at` = 澳門 **09-29 20:23:02** → 報表算昨日
- 即「結帳時間早過下單時間 7h24m」＝物理不可能。

**根因（兩層）**：

1. **兩個頁面日歸屬字段唔同**（設計分歧，本身已係 bug 溫床）：
   - 店鋪總覽 `/api/admin/merchants` → `loadPosStats()`：`status ∈ {settled,paid}` **AND `created_at` ∈ 澳門今日**（下單時間、`.gte` 無上限）
   - 營業報表 `RestaurantDailyReport` → `isSaleCountable()` AND `orderMatchesReportRange()`（經 `orderEventInstant()`：`settled_at → reopened_at → original_settled_at → updated_at → created_at`，**結帳時間優先**）
2. **澳覓（aomi）單的 `created_at` 被 +8 小時**（真兇）：
   - `TransactionGrabberExtension/aomi-bridge.js:262` → `occurredAt = states[0].stateDate`，係**澳門本地時間字串**（`"2026-09-29 19:46:59"`，無時區）；`background.js:206` 註釋已明寫「澳覓…本地時間字串 / mfood…均為 ISO」。
   - `src/lib/grabber/grabber-order.ts:539-542`：
     `const at = String(order.occurredAt ?? order.timeline?.created ?? "").trim(); const createdAt = at || now.toISOString();`
     → **原字串直接寫入 timestamptz**，Postgres 按 session TZ（UTC）解釋無時區字面量 ⇒ 本地 19:47 被存成 `19:47Z` ⇒ 讀出 +8 = 次日 03:47。
   - ✅ 平台單號自證：`TK001280260929194659140` 內嵌 `260929 194659` = 09-29 19:46:59 → 同 DB `created_at=19:47:07Z` 逐秒吻合。
   - **實測 4/4 澳覓單全部 -6.8～-7.5h；mfood 0/4、pos 0/43 完全正常**（mfood 的 `timeline.created` 自帶 offset）。

**結論：報表（20 單 / MOP 1,294）正確，總覽多算**。漂移係**雙向**的 —— 傍晚單漂去次日（09-29 那張）；凌晨單會漂去前一日，且 `created_at` 可能落在**未來**（現時 16:06，兩張 09-30 澳覓單 created_at 已是 21:03 / 21:43）。

**未做的根治方向**（待 J 確認）：
- POS 側防禦（唯一入口、最穩）：`grabber-order.ts` 寫 `created_at` 前做時區歸一化 —— 無時區字串一律按 `Asia/Macau` 解釋再轉 UTC ISO。
- 插件側（最近源頭）：aomi bridge 把 `stateDate` 轉成帶 `+08:00` 的 ISO。
- 總覽口徑對齊：`/api/admin/merchants` 改用 `orderEventInstant()` 同一套鏈（現時只認 `created_at`，同報表/交班永遠夾唔埋）。
- 歷史資料：需 SQL 修（`update pos_orders set created_at = created_at - interval '8 hours' where source='aomi'`）—— 執行前要先用更多樣本確認是否全量。
