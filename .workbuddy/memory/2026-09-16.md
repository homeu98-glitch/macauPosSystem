## ✅ 修復 .git（第二次中同款損壞，2026-09-16 完成）

**症狀**：所有 git 指令報 `fatal: not a git repository`。

**實測損壞範圍**（比 09-11 那次更重）：
- `.git/refs/**` 整個目錄不見（git 的 `is_git_directory()` 要求 `refs/` + `objects/` 同時存在，缺 refs 直接當你唔係 repo）
- 4 個 `.idx` 索引在、`.pack` 本體全冇 → `fsck` 報 `failed to load pack in position 0/1`
- 131 個 loose object 目錄全部空的
- 但 `.git/objects/pack/pack-ad35001fee...pack`（182MB）其實**完好**，`cat-file -t 3d71dba0` 回 `commit`

**關鍵命脈**：`.git/FETCH_HEAD` 記著 `3d71dba0`，`ls-remote` 確認 `origin/main` 就係同一個 SHA
→ **本地冇未推嘅 commit，遠端完整，冇丟任何歷史**。

**修復步驟（實測有效）**：
1. 先備份破損 `.git` → `C:/dev/macauPos/_git_backup_macauPosSystem_20260916`
2. `git ls-remote https://github.com/homeu98-glitch/macauPosSystem.git refs/heads/main` 取遠端 SHA
   （**唔靠 `origin` 名**，remote 設定可能已爛）
3. **手動重建 `refs/` 目錄樹**：`refs/heads/main`、`refs/remotes/origin/main`、`refs/remotes/origin/HEAD`
   各寫入 SHA（尾加 `\n`）。此步一做完 `rev-parse --show-toplevel` **即刻通過**
4. `git -c gc.auto=0 fetch --no-tags <原始URL> main`（**必須丟背景**，見下面坑）
5. 刪除**孤立 `.idx`**（無對應 `.pack` 者）→ 消除 `failed to load pack in position N`
6. 刪 `tmp_pack_*`（中斷下載殘留）、`multi-pack-index`（會引用已刪 idx）
7. 清理 reflog 中含遺失 SHA 的行 → **要同時比對第 1 欄（old）同第 2 欄（new）**
   （只比對 new 會漏，`fsck` 會繼續報 `invalid reflog entry`）
8. `git config --local gc.auto 0`（預防，見 docs/113）

**驗收（全部須 exit 0）**：
- `fsck --connectivity-only` / `fsck --full`
- **`status --porcelain=v1 --branch`** ← **GitHub Desktop 判準**，唔可以只驗無 `--branch` 嘅
- `branch -vv` → `main 3d71dba [origin/main] up`
- `count-objects -v` → `in-pack: 7603, packs: 1, garbage: 0`
- `log --oneline` → **495 個 commit**（09-01 起歷史完整保留）

**本次新發現的坑（要補入 docs/113）**：
- ⚠️ **`--git-dir=<path>` 參數一樣無效**（`fatal: not a git repository: '...'`）——
  缺 `refs/` 時 git 直接拒絕，唔係認唔到路徑。**要修好 `refs/` 先有可能用任何指令。**
- ⚠️ 用 node `execFileSync` 跑長 fetch 會被 timeout **SIGTERM**，且**物件可能已部分寫入**
  （留低 `tmp_pack_*` 54MB 殘留）。改用 `run_in_background`。
- ⚠️ reflog 過濾必須**兩欄都比對**。

## 🔴🔴 收口：`POS_DEVICE_TOKEN_SECRET` / `POS_REQUIRE_DEVICE_AUTH` 都冇設（2026-09-16 01:04 用戶確認）

### 用戶提供嘅事實
- `POS_DEVICE_TOKEN_SECRET` —— **冇設**
- `POS_REQUIRE_DEVICE_AUTH` —— **冇設**
- 剛剛把 `SUPABASE_URL` / `SUPABASE_ANON_KEY` **重新再 save 一次**

### 推導（呢兩條 env 都冇設，會發生咩事）

`resolveSecret()`（`pos-device-token.ts:50-57`）三段 fallback：
```
POS_DEVICE_TOKEN_SECRET → ADMIN_SESSION_SECRET → SUPABASE_SERVICE_ROLE_KEY / _KEY
```
⇒ 只要 **`SUPABASE_SERVICE_ROLE_KEY` 有設**，簽名密鑰就**照樣拿得到**，token 照簽得出。**唔會因為冇 `POS_DEVICE_TOKEN_SECRET` 而壞。**

`isPosDeviceAuthRequired()`（`pos-device-token.ts:136-140`）：
```
raw === undefined || raw === "" → return true   // ← fail closed！
```
⇒ **冇設 `POS_REQUIRE_DEVICE_AUTH` ＝ 閘照樣開著**（唔係關）。**呢個直覺陷阱好易中** ——
「冇設」≠「關閉」，係「強制」。

### 🔴 決定性實測（線上）

| 端點 | 實測 | 判讀 |
|---|---|---|
| `POST /api/pos/device-token` 空 body | `400 {"error":"缺少 accessToken。"}` | 端點活著，rate-limit 通過 |
| `POST /api/pos/device-token` 假 token | `401 {"error":"Ledger 會話已失效，請重新登入。"}` | **證明唔係 503「系統未設定終端憑證密鑰」** ⇒ **secret 鏈有值，簽發能力正常！** |
| `GET /api/pos/state?storeId=test-store` | `401 「未經授權：讀取店舖資料需要 POS 終端憑證」` | 閘生效 |
| `GET /api/pos/print-jobs/status?storeId=…` | `401 「未經授權：需要 POS 終端憑證」` | 閘生效 |

**⇒ 關鍵結論：`SUPABASE_SERVICE_ROLE_KEY` 有設，簽發路徑健康。**
**所以 `POS_DEVICE_TOKEN_SECRET` 冇設 ≠ 問題根源。**
唯一後果＝簽名密鑰係「借」service role key，日後若換 service role key，所有 token 一齊失效（可接受）。

### ⇒ 真正的病因收窄到：**iPad 手上嘅 token 已經失效／過期**

`refreshPosDeviceTokenIfNeeded()` 續期失敗 → 冇 token → 打 `pair-status` 得 401 →
`relay-pairing-panel` 顯示「配對失敗」。

**修復＝iPad 重新登入 POS 帳號**（唔使改任何 env、唔使 redeploy）。
