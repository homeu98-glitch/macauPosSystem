## 多憑證可行性確認（店主登入主店後再輸其他店 PIN）

讀碼結論：**技術上成立**。Ledger 登入＝`phone→email` + `PIN→password`（`pin.server.ts`）→ Supabase Auth 回 `access_token`＋`refresh_token`，係不透明字串，可同時持 N 份（按 merchantId 索引）；`POST /api/ledger/login` 已喺 server 端換票，PIN 唔使落地。

三個硬限制（唔改就會斷層）：
1. `getLedgerSupabaseClient()` 係 **singleton**（`persistSession:false`，session 存記憶體）；`ensureLedgerSession()` single-flight 假設「一個身份」⇒ 唔可以喺同一個 client 持 N 個身份。
2. refresh token **會輪換**（`session.ts:37-47` 已記錄踩過嘅坑）⇒ N 店各自刷，client 側做會互相踩。
3. `get_merchant_report_summary` **冇 p_merchant_id**，商戶由 `auth.uid()` 推導 ⇒ 一個 JWT 只能對應一店，跨店要逐店 token → 逐店 RPC → POS 端彙總。

🔴 新發現（未驗證）：`/api/ledger/login` 查 `merchant_staff` 用 `.limit(1)` ⇒ 若一個 Ledger 帳號本身已綁多店，會被硬截成 1 店。要先查 `merchant_staff where user_id=<uid>` 有幾行，先知要唔要老闆輸 5 次 PIN。
⚠️ 本機冇 `.env.local`（冇 `AUTH_PIN_PEPPER`）⇒ 無法由本機直接驗證，需 Vercel env 或 Ledger 側查。

設計結論：多店能力**唔好改 POS 嘅單店 session**（`session.merchantId` 遍地都係），應該做成 admin panel 側嘅「多店主控台」；憑證存 server DB（唔存瀏覽器），由 server 代刷 refresh。
