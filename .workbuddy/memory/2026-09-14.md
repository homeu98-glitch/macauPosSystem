## 🔴🔴 走數實案：收銀台「會員扣款」全額用餘額時**完全冇扣**（MOP 85）

**J 原話**：「我先是下了單, 然後我成功扣了款, 然後我又在那張桌台下了單, 然後我要結帳,
結帳的時候我是選了會員扣款… 他說是『客人已支付，完成訂單』… 然後我按下去後,
在 ledger 那邊只扣了我 75（掃碼嗰筆）, **沒有扣到我新下單的那一筆**。」

截圖數據：小計 **MOP 160**、客人已支付 **MOP 75**（綠）、剩餘需收 **MOP 0**、
**會員扣款 MOP 85**、支付方式選中「會員餘額 可用 MOP 219 · 本次扣 MOP 85」。

### 根因（`pos-app.tsx`）—— 判斷條件太闊
```ts
// L1982
const paymentSummary = { ..., memberDeduction,
  total: Math.max(0, payableBeforeMember - memberDeduction), };   // ← total 已減計劃扣款
```
```tsx
// 撳鈕 onClick（L6449）
if (paymentSummary.total <= 0 && paymentSummary.prepaidAmount > 0) {
  completeOnlinePaidOrder();   // ← 直接完成，唔會 confirmPayment()、唔扣款
  return;
}
```

**逐步重演**：`payableBeforeMember` = 160 − 75 = 85；店員選會員餘額 → `memberDeduction` = 85
→ `total` = 85 − 85 = **0** → 條件成立 → `completeOnlinePaidOrder()` → **MOP 85 走數**。

⇒ **`total <= 0` 唔等於「已付齊」** —— 因為 `total` 已減咗 `memberDeduction`（**計劃**扣款）。

### 兩個問題嘅答案（我自己查，唔應該問 J）
1. **「客人已支付，完成訂單」原意** = `completeOnlinePaidOrder()`：客人喺 Ledger／掃碼端
   已經付**全款**（`paymentMethod: "線上已支付"`）→ 收銀台只需確認完成。**設計正確**，
   只係判斷條件太闊。
2. **收銀台「會員扣款」只有「去結帳」才會真扣** ✅ ——
   路徑 = `confirmPayment()` → `runCheckout()` → `executeLedgerMemberCheckout()`（`merchant_apply_pos_txn`）。
   而 `total <= 0 && prepaidAmount > 0` 時**永遠去唔到呢條路**。

### 修正
新增 `isOnlinePaidComplete`（`paymentSummary` 之後）：
```ts
const isOnlinePaidComplete =
  !(useMemberBalance && memberDeduction > 0) &&          // ← 關鍵：有計劃扣款就唔算已付齊
  paymentSummary.total <= 0 &&
  paymentSummary.prepaidAmount > 0;
```
三處改用它：`onClick` early return（`completeOnlinePaidOrder`）、掣文字、以及原本 `total<=0` 判斷。
⇒ `memberDeduction > 0` 時一定落 `confirmPayment("會員餘額")` → 真扣款 ✅

⚠️ 呢個係**既有 bug**（唔係今次會員登入改動引入）。只要「全額用會員餘額付」就會中招；
部分扣（例如應收 100 扣 50）因為 `total = 50 > 0` 反而正常 → 所以一直冇被發現。

## 🔴🔴 第二個走數實案：`runCheckout` 靜默行非會員路徑（會員扣款完全冇執行）

**J 情境**（同一張 A03 掃碼單）：① 掃碼落單扣 75 ✅ → ② 商家幫加 1 個麵（桌台見到 2 項）
→ ③ 前台結帳選「會員餘額」（`memberDeduction` = 85、掣已變「去結帳」）→ ④ 撳落去 →
**Ledger 完全冇扣、冇任何 toast、餘額不變**；而且**收據只印 1 項 $75 但總金額寫 MOP 160**。

**J 確認嘅三點**（關鍵）：
- 桌台**有**兩個面（=`paymentBase` 正確）
- Ledger **冇扣**（只有掃碼嗰筆 75）
- 收據 items 來源 = **線上**（`order.items`）→ 只 1 項
- 撳完**冇 toast**、餘額**冇變**

### 根因：`runCheckout` 有兩條路（`pos-app.tsx`）
```ts
const runCheckout = async (targetOrder: PosOrder) => {
  if (memberLedgerOpsNeeded && merchantId && ledgerMember) {
    ... executeLedgerMemberCheckout(...) ...   // ← 真扣款
    return;
  }
  applyPaymentToOrder(targetOrder);            // ← 靜默、冇扣款、冇 toast（L4030）
};
```
**「冇 toast + 冇扣款」完全符合第二條路** ⇒ `memberLedgerOpsNeeded` / `merchantId` / `ledgerMember`
其中一個 falsy。而 `merchantId` 若 null 會有 toast（J 冇見到）→ 所以係
`ledgerMember` 或 `memberLedgerOpsNeeded` falsy。

⚠️ **確切係邊個仍未確定**（`useMemberBalance` 由客人 toggle 設，L1961 嘅 reset 只喺「號碼非 8 位」時發生）。

### 修正（防走數，唔係猜真因）
喺 `runCheckout` 第二條路之前加硬閘：
```ts
if (useMemberBalance && memberDeduction > 0) {
  setToast({ type:"info", message:"未能執行會員扣款（會員資料或商戶登入狀態不完整），已取消結帳。請重新輸入會員號碼查詢後再試。" });
  return;   // ← 寧願唔結帳，都唔可以標記已付款而冇扣錢
}
```
**理由**：走數（標記已付款 + 冇扣錢 + 冇提示）比「結唔到帳」嚴重得多；
而且呢個 toast 會**直接暴露真因**（下次一撳就知）。
