## 4. 修復後仍然係大戶嘅三項（逐項：根因 → 對策）

### ① 舊分頁：43.5 MB/小時（51%）← 最大
- **實測**：部署後 122 次 / 68 分鐘 ＝ **1.79 次/分鐘（每 ~33 秒）**，每次 404 KB。
- **根因**：**頻率**冇變。舊 JS 冇輪詢閘（2026-09-21 修好嘅自激迴圈只喺新 bundle 生效），
  所以「減 bytes」只係一半答案。
- ✅ **已補 P0b（今次修）**：同一部機（`ip + user-agent`）**90 秒內第二次 legacy 全量拉取 → 回空骨架**
  （`mode=legacyThrottled`）。空骨架對 client 係 no-op：`orders: []`／`queue: []`／`printJobs: []`／
  `localSettings: null` 全部有守門 ⇒ 本地資料完整保留。
  🔴 一定要帶 `incremental: true`，否則客戶端會以為「雲端真係冇呢啲單」而**隔離全店未結單**（已寫成守衛）。
- **效果估算**：1.79 → 0.67 次/分鐘真拉取 ⇒ 43.5 → **~3.6 MB/小時（−92%）**。

### ② 訂單頁 backfill：6.4 MB/小時（289 KB × 0.37 次/分）← 🔴 我上一版嘅 bug
- **實測**：`limit=200 offset=0 cols=default start=-` 共 **136 次、38.4 MB、平均 289 KB**，**冇日期範圍、冇投影**。
- **根因**：我 P3 令訂單頁傳 `&ordersOnly=1&since=…`，但 server 寫死
  `incremental = Boolean(since) && !ordersOnly` ⇒ **`since` 被無視** ⇒ P3 完全失效。
- ✅ **已修（今次）**：`ordersOnly` 之下**有 `since` 都要做增量**（單腿 `updated_at > since`）。
  安全前提：**只有主動傳 `since` 嘅 caller 才受影響**；報表／交班／對賬守護一律唔傳 ⇒ 完整區間語義不變。
- **效果估算**：289 KB → ~3 KB ⇒ 6.4 → **~0.07 MB/小時（−99%）**。

### ③ 報表全量：每次 482 KB（約每 20–40 分鐘一次）
- **實測**：`limit=5000 start=-`（**無 range**）12 次、每次 460–482 KB，`orders` 由 305 逐次升到 325
  ⇒ 每次都重拉「今日全部訂單」。
- **根因**：報表頁走「全部／無日期範圍」嗰條路（`start=-`），而**唔係**用細範圍。
- **對策（未做）**：報表預設／快取（例如同日同範圍加 ETag 或 60 秒 memo）。
  ⚠️ **唔可以**改成增量或本地計算 —— 專案明文禁止改「報表＝雲端真值」口徑。

## 5. 為何「關店」冇擋住？（輪詢閘嘅覆蓋範圍）

| 來源 | 受唔受「關店」影響 | 實測 |
|---|---|---|
| 舊 JS 全量迴圈 | ❌ 完全唔受（**冇閘**） | 1.79 次/分，關店照拉 |
| `triggered` 拉取（開頁／Realtime 重連／手勢） | ❌ 唔受（設計如此：事件驅動自帶頻率上界） | `src=mount` 30 次 |
| 報表 / 訂單頁 / 對賬守護（`ordersOnly`） | ❌ 唔受（本來就唔經輪詢閘） | 281 次 |
| 週期輪詢（POS 主頁 `state`） | ✅ 受（兩條通路都關 → 停） | 週期拉取已見收斂 |
| **APK claim** | ❌ 唔受（24/7） | **152 次 / 192 分鐘 ＝ 每 76 秒**（bytes 細，唔係大戶） |
| Realtime WebSocket | ✅ 只係推送 | 16 條連線 / 192 分鐘；Dashboard 顯示佔 **2.1%** |

⚠️ 另一個易誤判：**只關一條通路**（例如只關線下、線上仍開）按設計會繼續監察（殘留通道警示）——
呢個係刻意嘅，唔算 bug。
