# 補建事故報告：取餐碼 002／003 被移去今日（2026-09-24）

> 症狀：撳「補建入 POS」補 4 張之後，報表由 **28 張／MOP 1,778** 變成 **37 張／MOP 2,423**，
> 而且同日出現**兩個相同取餐碼**。商家以為「補完更錯」。

---

## 1. 真因（兩層疊加，兩層都係我今次新增功能引起）

### 第一層：補建判準太窄 ⇒ 誤把「昨日已入帳」嘅單當成「漏帳」

補建目標來自：

```ts
const countableOnlineOrders = onlineOrders.filter((o) => !posOnlineIds.has(o.id));
```

而 `posOnlineIds` 當時**只來自報表當前 range 嘅 `orders`**（今日雲端單）。
⇒ 較早日期（09-23）已經有 POS 單嘅 Ledger 單，因為「唔喺今日 range」而被判「未入 POS」
⇒ 被當成漏帳單補建 ⇒ `upsert` **覆蓋**原有 POS 單。

### 第二層：`updated_at` 係 server 蓋章 ⇒ 舊單日期被推成今日

`/api/pos/sync` 明文（`route.ts:342-349`）：

> `updated_at` 改為 **server 蓋章**（Vercel/DB 時鐘）之後，LWW 比較必須用同鐘域嘅 client 時間…

⇒ 我原本寫嘅 `updatedAtOverride`（保留 Ledger 事件時間）**對雲端 `updated_at` 完全無效**，
只有本地那個生效。
⇒ 兩張 09-23 嘅單，`updated_at` 被推成 **09-24T13:24Z**。

**合併後果**：

| | 09-23 報表 | 09-24 報表 |
|---|---|---|
| 原本 | 有 002（69）、003（129） | — |
| 事故後 | **少咗 2 張** | **多咗 2 張（59＋129）** |

而且取餐碼**每日重用** ⇒ 今日同時有「09-23 移過來嘅 002」同「今日原本嘅 002」
⇒ 睇落就係「重複」。

## 6. 教訓（寫入協作備忘）

- 凡「補建／回填」類功能，判斷「係唔係已經有」**唔可以只用當前 range**；
  必須查**全量**（本機或雲端）。
- **雲端 `updated_at` 係 server 蓋章** ⇒ 任何「重推」都會變成「改歸屬日」。
  凡寫入既有單之前，一定要先確認「呢張單係唔係真係唔存在」。
- 補建類操作**唔應該**用 Ledger 明細重建既有單（會覆蓋店內加菜）；
  只可以用於「從來冇本地單」嘅情況。
