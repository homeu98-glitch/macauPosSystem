## 二、為什麼 website 顯示正常（而你實際印不出）

這是你這次觀察到的最矛盾之處，也是最容易誤導的地方：

```
pair-status 回的 paired: true
  → 只是證明「pos_print_agents 表裡有一行」
  → 這是一個【歷史事實】，不是【即時狀態】
  → APK 從 14:25 之後就沒有再心跳，但那一行仍然在
  → 所以 paired 永遠為真 ⇒ Web 永遠綠
```

**⇒ 「Web 綠」與「App 已死」可以同時成立。** 這不是 bug，是判準本身只回答了一個錯誤的問題。

唯一會反映即時狀態的是 `lastSeenAt`，換算成「最後心跳 N 分鐘前」後：

| 顯示位置 | 是否顯示 | 前提條件 |
|---|---|---|
| `/prints`（打印中心）紅 banner | ✅ 會顯示「N 分鐘前（疑似離線）」 | **必須先有「雲端未完成任務」才會 render** |
| `/`（收銀台） | ❌ **完全看不到** | — |

⇒ 收銀員只看到「已發送」，然後一張紙都沒有，也沒有任何紅標。
**這正是積壓可以拖 4 天（9/11 → 9/15）而無人處理的直接原因。**

## 六、建議的確認與修復方式

### 步驟 0：先確認沒有陳舊積壓會一次爆紙 ⚠️

重啟中繼機**之前**必須先確認。`ttl` 目前**只在 insert 時寫入**，舊行 `ttl` 恆為 NULL ⇒ **永不過期**。

執行救援 SQL 的唯讀段：
`tools/2026-09-15-void-stale-pending-print-jobs.sql` §1.3

目前只剩 4 張 pending（最近 40–151 分鐘），數量可控。若確認這 4 張已無需要，跑 §2 作廢。

### 步驟 1：到 Sunmi 主機前實地檢查

- App 還在執行嗎？狀態欄寫什麼？
  - 「POS 雲端未設定」→ 缺 supabaseUrl/anonKey
  - 「已連線（Realtime）」→ 有連上但在訂錯誤的表
  - 完全沒有 App → 被系統殺掉了
- 主機是否開機、有電、有網路？

### 步驟 2：用 SQL Editor 查中繼機真實心跳（service_role 才看得到）

```sql
select agent_id, store_id, name,
       revoked_at,
       last_seen_at at time zone 'Asia/Macau' as 最後心跳_澳門,
       round(extract(epoch from (now() - last_seen_at))/60) as 幾分鐘前
  from public.pos_print_agents
 order by last_seen_at desc;
```

判讀：
- `幾分鐘前 > 5` → 確認離線（與本報告一致）
- `revoked_at` 有值 → 是原因 #4，重新配對即可

### 步驟 3：重啟 Sunmi APK → 確認心跳恢復

看 `/prints` 紅 banner：
- 「最後心跳 N 分鐘前（疑似離線）」→ 變回 **N < 5（無「疑似離線」）** = 已恢復
- 若仍顯示離線 → 到「設置 → 打印中繼」重新配對

### 步驟 4：為需要的單據手動補打

交班單 → 交班頁；收據 → 訂單頁「補打帳單」；廚房單 → 打印中心重打。
**手動補打是有意識的動作，不會一次爆 4 張。**

## 八、診斷手法（可重用，不需任何 secret）

1. 從線上 bundle（`_next/static/*.js`）抽出 `eyJ…` 形式的 anon key
2. 解 base64 中段，讀 `ref` 欄位辨識是哪個 Supabase 專案
3. 以該 key 唯讀打 PostgREST API 查 `pos_print_jobs`

**判斷中繼機死活的唯一鐵證**：
- 有 `claimed_by` 非 NULL 的行 → 中繼機活著
- 全部 NULL 且 `attempts = 0` → **從來沒有 claim**（機死，不是印不出）
- `attempts > 0` + `AGENT_FAILED` → 才是硬件／出紙問題
