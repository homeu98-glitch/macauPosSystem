# 餐飲店每日營運總結報表 — 設計方案

> 一份讓老闆每天開店／打烊前 30 秒就能掌握店內營運、並據此做優化決策的總結報表。
> 目標讀者：店主 / 店長。設計原則：一眼掌握核心、資訊分層、與現有 POS 風格一致、離線優先、澳門時區。

---

## 1. 目標與使用者

| 項目 | 說明 |
|------|------|
| 使用者 | 店主、店長（非收銀員） |
| 使用場景 | 每日開店前看昨日/今日即時狀況；每週/每月做趨勢與採購決策 |
| 核心訴求 | 「今日賺多少、食材花多少、哪道菜最旺、出餐順唔順、會員有冇儲值、有咩要立刻執」 |
| 成功標準 | 老闆唔使問人、唔使開 Excel，打開呢一頁就知今日要點做 |

報表整合**營運數據**（訂單、出餐、人流、桌台）與**庫存數據**（買貨成本、食材消耗、沽清），並產出**自動化優化建議**。

---

## 2. 設計原則

1. **核心指標前置**：營業額、毛利、訂單數、客單價、人流、會員充值放最頂「KPI 帶」，字大、對比昨日。
2. **資訊分層**：KPI 帶（一眼）→ 九大模塊（詳情）→ 優化建議（行動）。
3. **風格一致**：沿用現有 `reports-dashboard.tsx` 的餐飲視覺語言（orange 主色、slate 底、white 卡、`rounded-2xl`、頂部右側篩選）。
4. **篩選統一**：全系統共用 `REPORT_RANGE_OPTIONS`（`src/lib/ledger/report-period.ts`），順序固定為「今天 / 昨天 / 7天 / 30天 / 全部」，置於右上角。
5. **離線優先**：本機訂單、庫存來自 localStorage / 本地聚合；Ledger 會員/線上數據失敗時降級顯示「未能連線」，不阻塞。
6. **澳門時區**：所有日期邊界用 `macauDateKey` / `macauTodayRange`（`report-period.ts`）計算，避免 UTC 偏移。

## 3. 統一時間篩選（右上角）

沿用既有常數，標籤依用戶指定順序與用詞：

```ts

  { key: "today",     label: "今天" },
  { key: "yesterday", label: "昨天" },
  { key: "7d",        label: "7天" },
  { key: "30d",       label: "30天" },
  { key: "all",       label: "全部" },

```

- **位置**：頁面標題列右側，與 `salon/reports.tsx` 的 `justify-between` 標題＋篩選排列方式一致。
- **樣式**：未選 `bg-slate-100 text-slate-700`；選中 `bg-orange-500 text-white`（`rounded-lg`，餐飲主色）。
- **作用範圍**：切換後所有模塊與 KPI 同步重算，含 Ledger 線上/會員數據（`getMerchantReportSummary(range)`）與買貨成本（`fetchPurchaseSummary(account, range)`）。
- **一致性要求**：salon 報表現用 `today/week/all` 三鍵，建議後續一併升級為此五鍵，全系統篩選體驗統一。

## 5. 核心 KPI 帶（頂層 · 一眼掌握）

| KPI | 公式 | 資料源 | 備註 |
|-----|------|--------|------|
| 營業額 | Σ settled 單 `total`（本機）＋ `orderPaidMop`（Ledger 線上） | `loadOrders()` + `getMerchantReportSummary` | 主色高亮 |
| 毛利 | 營業額 − 食材總消耗金額（見模塊 1） | 同上 | 主色高亮；無 BOM 時用買貨成本估 |
| 訂單數 | settled 單數（線上＋線下） | 同上 | — |
| 客單價 | 營業額 ÷ 訂單數 | 計算 | 同環比昨日 |
| 人流 / 覆蓋人數 | Σ `partySize`（covers） | `PosOrder.partySize` | 見 §10 人流計數缺口 |
| 會員充值 | `topupMop` | Ledger `getMerchantReportSummary` | 含「會員數」小標 |

每張卡顯示**較昨日變幅箭頭**（▲/▼ + %），讓老闆一眼知今日好定唔好。

## 6. 九大功能模塊詳細規格

### 模塊 1 — 本月食材消耗數量及金額統計
- **目的**：知今日/本月食材花咗幾多，對住營業額睇成本率。
- **資料源**：買貨收據（`StatReceipt` / `fetchPurchaseSummary`）提供每項 `unit_price`；消耗數量需 BOM（見 §10）。
- **計算**：
  - 消耗數量(i) = Σₘ 銷量(m) × `bom[m][i]`（每道菜用幾多料）
  - 消耗金額(i) = 消耗數量(i) × 近期均價(i)（來自買貨收據）
  - 食材總消耗金額 = Σᵢ 消耗金額(i)
- **視覺**：大數字「總消耗金額」＋「總消耗數量（項次）」＋ 成本率%；無 BOM 時顯示「買貨成本（已付）」作降級並標注「估算」。
- **位置**：左側與模塊 2 並排（成本相關一組）。

### 模塊 2 — 每種食材使用量排行
- **目的**：邊種料最搶手、邊種最燒錢，指導採購與議價。
- **資料源**：同模塊 1（BOM × 銷量）。
- **計算**：每食材 消耗數量降冪排行；附「金額」與「佔食材成本 %」。
- **視覺**：橫向條形榜（Top 10），每條顯示 數量(單位) + MOP + 佔比進度條。
- **位置**：模塊 1 右側。

### 模塊 3 — 菜品銷售量統計（線上線下合併＋渠道標籤）
- **目的**：邊道菜旺、線上定線下賣得多。
- **資料源**：
  - 線下：`loadOrders()` 中 `status=settled` 且無 `onlineOrderId` 的單。
  - 線上：Ledger 線上單（`onlineOrderId` 有值，或 `getMerchantReportSummary` 的 `orderCount/orderPaidMop` 細項）。
- **計算**：每 `menuItemId` 合併 線下 qty + 線上 qty；標 `渠道=線下/線上/混合`。
- **視覺**：排行表，欄＝菜品 / 總銷量 / 線下 / 線上（渠道色標）/ 營業額；線上單獨用藍標、線下用灰標、混合用雙色。
- **位置**：左上主區（最寬），因係每日決策核心。

### 模塊 4 — 出餐時間數據統計
- **目的**：出餐順唔順、尖峰會唔會塞廚房。
- **資料源**：需新增時間戳（見 §10）；過渡期用 `createdAt → settled/ready` 估算。
- **計算**：出餐時間 = `servedAt − sentToKitchenAt`；報 **平均 / 中位數 / P95**；按小時分桶睇尖峰。
- **視覺**：整體三數字卡 ＋ 每小時平均出餐時間折線/長條（標紅 > 閾值，預設 15 分鐘可配）。
- **位置**：左下，與桌台並排。

### 模塊 5 — 當日人流數據
- **目的**：今日幾多人入店 / 坐咗幾多檯。
- **資料源**：`partySize` 求和（覆蓋人數）作降級；精確人流需新增門口計數（見 §10）。
- **計算**：覆蓋人數 = Σ `partySize`；若有人流計數則直接用計數。
- **視覺**：大數字 ＋ 尖峰時段熱力圖（每小時人次）＋ 較昨日對比。
- **位置**：下方左，與付款/渠道並排。

### 模塊 6 — 會員充值金額及會員數目
- **目的**：會員引擎健唔健康、現金回流幾多。
- **資料源**：`getMerchantReportSummary().topupMop`（充值）；會員數需 Ledger 會員清單計數（新增 RPC 或 `list_members` count，見 §10）。
- **計算**：充值金額 = `topupMop`；會員數 = 區間內活躍會員數 / 累計會員數；會員消費佔比 = `orderBalancePaidMop ÷ 營業額`。
- **視覺**：充值金額大卡 ＋ 會員數小標 ＋ 會員消費佔比條。
- **位置**：下方右，與沽清並排。

### 模塊 7 — 沽清菜品數量
- **目的**：有幾多菜賣到斷貨，影響营收同客人體驗。
- **資料源**：現有 `soldout` 清單（`/api/inventory/soldout` + `soldout-page.tsx` 狀態）。
- **計算**：目前標記沽清的 `menuItem` 數量；列出菜名。
- **視覺**：紅標數量卡 ＋ 沽清菜名 chips；附「低庫存預警」（見補充項）。
- **位置**：下方右，與會員並排。

### 模塊 8 — 最熱門桌台使用排行
- **目的**：邊張枱最旺、翻枱快唔快，助排枱與擺位。
- **資料源**：`PosOrder.tableId/tableName` + `partySize` + 開枱/結帳時間。
- **計算**：每枱 訂單數降冪；翻台率 = 訂單數 ÷ 營業時數（或 covers ÷ capacity）。
- **視覺**：排行表（枱名 / 單數 / 覆蓋人數 / 翻台率）。
- **位置**：左下，與出餐時間並排。

### 模塊 9 — 基於數據的自動化優化建議
- **目的**：把數字轉成「老闆今日要做咩」。見 §8 規則表。
- **視覺**：全寬醒目面板，每條建議帶 優先級（紅/橙/灰）、一句發現、一句行動。
- **位置**：最底，壓軸。

## 7. 補充報表項目（對營運有額外價值）

在九大模塊之外，建議加以下項目，進一步提升決策力：

| 補充項 | 價值 | 資料源 |
|--------|------|--------|
| **食材成本率 / 毛利趨勢** | 直接知呢單生意賺唔賺 | 模塊 1 ＋ 營業額 |
| **客單價 / 人均消費** | 知要唔要推升單價（加購/套餐） | KPI 帶 |
| **翻台率** | 座位利用效率，決定加唔加位 | 模塊 8 |
| **退菜 / 廢棄率** | 出餐品質、訓練缺口 | `OrderItem.voided` / `voidedItems` |
| **折扣佔比** | 優惠係咪送太多 | `discountAmount ÷ 營業額` |
| **尖峰時段熱力圖** | 排班、備料、人手調度 | 訂單 by hour |
| **低庫存預警** | 主動補貨，避免沽清 | 庫存 par level（新增） |
| **員工 / 收銀業績** | 激勵與排班 | `PosOrder` 操作人 / Ledger |
| **線上渠道佔比** | 線上推廣 ROI | 模塊 3 渠道拆分 |
| **同環比（vs 昨日 / 7日均值）** | 今日好定差 | 全模塊對比 |

## 8. 自動化優化建議引擎（模塊 9 規則）

規則為純函式，輸入各模塊聚合結果，輸出建議陣列。每條含 `level`（紅=立即/橙=關注/灰=資訊）、`finding`、`action`。

| # | 觸發條件（示例閾值） | 發現 | 建議行動 |
|---|----------------------|------|----------|
| R1 | 食材成本率 > 35% | 食材成本偏高，蠶食毛利 | 檢討高耗料菜品售價或換供應商議價 |
| R2 | 高銷菜嘅食材庫存 < 安全存量 | 旺菜快冇料，隨時沽清 | 今日優先補貨該食材 |
| R3 | 尖峰時段平均出餐 > 15 分 | 午/晚市出餐塞車 | 尖峰加開廚房人手 / 簡化工序 / 預製 |
| R4 | 線上渠道佔比 7日升 > 5pt | 線上單明顯增長 | 加強線上推廣、確保廚房產能跟到 |
| R5 | 會員充值較 7日均值跌 > 30% | 會員現金回流偏弱 | 推限時儲值贈金活動 |
| R6 | 退菜率 > 3% | 出餐品質/落單錯誤偏多 | 檢視退菜原因、加強培训 |
| R7 | 折扣佔比 > 15% | 優惠送太多 | 檢討優惠門檻，避免無謂折讓 |
| R8 | 沽清數量 ≥ 3 | 斷貨影響营收同體驗 | 即日補貨或暫時調整推薦主菜 |
| R9 | 翻台率最低枱長期偏低 | 擺位/排枱可優化 | 重新規劃該區座位或併枱 |
| R10 | 營業額較 7日均值跌 > 20% | 今日明顯偏淡 | 推限時優惠 / 喚醒沉睡會員 |

規則可配置（閾值存 `PosLocalSettings`），日後加規則唔使改 UI。

## 10. 前置數據準備 / Schema 缺口

> 以下缺口決定「精確度」。建議分兩階段：MVP 先用估算/降級上線，儀器化後補精確值。

1. **BOM 配方表（模塊 1/2 必須）**
   - 新增 `menu_item_ingredients`：`{ menuItemId, ingredientName, quantity, unit }`。
   - 消耗 = 銷量 × BOM；金額 = 消耗 × 近期均價（買貨收據）。
   - 過渡：無 BOM 時，模塊 1/2 顯示「買貨成本（已付）」並標「估算」，唔block 其他模塊。

2. **出餐時間戳（模塊 4）**
   - `PosOrder` 加 `sentToKitchenAt?`、`servedAt?`（ISO）；落單送廚房寫前者，標 ready/取餐寫後者。
   - 過渡：用 `createdAt → settled` 估算，標「估算」。

3. **人流計數（模塊 5）**
   - 精確：收銀/樓面手動 +1 或攝像頭計數，存 `daily_footfall`。
   - 降級：Σ `partySize` 作「覆蓋人數」，標「估算」。

4. **會員數（模塊 6）**
   - 新增 Ledger RPC `get_merchant_member_summary` 回傳 `memberCount`；或前端對 `list_members` 計數（注意分頁）。

5. **低庫存 par level（補充項）**
   - `inventory_items` 加 `parLevel`；低於即預警。

## 11. 設計語言與元件

沿用 `globals.css` 變數與 `reports-dashboard.tsx` 餐飲風格：

- 主色 `--primary`（indigo #4f46e5）；餐飲報表強調色 **orange-500**（篩選選中、KPI 高亮）。

- 卡內小標 `text-xs text-slate-500`；大數 `text-2xl/3xl font-semibold text-slate-900`。

## 12. 實施階段

- **Phase A — MVP（唔改 schema）**：KPI 帶、模塊 3/6/7/8、補充（客單價/退菜/折扣/尖峰/同環比）、優化建議（R3/R5/R6/R7/R8/R10 用估算值）。即日可上。

- **Phase C — 硬化**：每日自動快照（開店推送/Email）、CSV/PDF 導出、離線緩存、規則閾值設定 UI、salon 報表同步五鍵篩選。
