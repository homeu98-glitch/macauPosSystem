## 二維碼「太長，無法生成 QR」全部出現 + kiosk 單 POS 睇唔到（2026-08-22 後段，再排查）

用戶報：① kiosk 落單後 POS 睇唔到新單但單號正常；② 掃碼點餐 QR 全部顯示「太長，無法生成 QR（請用複製網址）」。

**② QR 根因（已修，確定）**：`src/lib/qrcode.ts` 自包含編碼器只支援 v1–5（byte mode EC-L 上限 = data 108 − 2 = 106 bytes）。而家 `storeId` 係 Ledger `merchant_id` UUID（36 bytes）+ 中文 `storeName`，URL ≈ 120–142 bytes 超過 106 → `encodeQrMatrix` 回 null → 全部顯示「太長」。
修法：(a) 編碼器擴充到 v6（size 41 / data 136 / ec 18，單 block，v1–6 唔使 version-info 模塊；alignment 中心 (34,34) 按標準 placement）；(b) `kiosk-qr-panel.tsx` 由 URL 移除 `&storeName=`（手機 `/menu` 已按 `scanStoreId` 去 `/api/pos/bootstrap` 攞返所屬店真名，`displayStoreName` fallback `bootstrap.storeName`，所以移除唔影響店名顯示，仲更準確）。移除後 URL ≈ 94–106 bytes，v5/v6 都穩陣。Node type-strip 測試確認 120 bytes URL → size=41（v6）OK、94 bytes → v5 OK。

**① POS 睇唔到 kiosk 單根因（硬化 + 診斷）**：happy-path 代碼其實正確——kiosk 落單 `store_id = binding.storeId (= merchantId UUID)`，POS 用 `authSession.merchantId` 過濾 realtime + 15s 輪詢 `/api/pos/orders?storeId=merchantId`，兩者應一致；`mergeOrderLists` / 顯示 tab 冇過濾。真兇係 **`/api/pos/sync` 靜默失敗**：舊碼 `if (supabase && events.length>0){...}` 唔 check upsert error，且 `supabase` 為 null（server env 缺）時都回 `ok:true` → kiosk 收到 200 → 顯示成功單號（所以「單號正常」），但單根本冇寫入 `pos_orders` → POS 永遠睇唔到。而家硬化：(a) `supabase` 為 null 且有 events → 返 503 + 明確 error；(b) 每個 upsert 收 `error`，有就收齊回 500 + 第一個 error message；(c) `submitKioskOrder` 解析回應，`!res.ok || body.ok===false` 就 throw 真 error（kiosk 改顯示真錯誤而唔係假成功）。
→ 部署後重測：若 kiosk 現顯示 error，就係 server 端 DB/env/schema 問題（relay 個 error 即可定位）；若仍顯示成功但 POS 唔見，就係 kiosk 綁店 merchantId ≠ POS 登入 merchantId（同店必須同一 Ledger 帳號），或 `pos_orders` 表喺共用 Supabase 項目未建（該表由 Macau-Ledger repo migration 建立，本 repo 只加 policy/publication）。

## 0010_kiosk_realtime.sql 根本冇跑成 → ② POS 收唔到 kiosk 單嘅真兇（再排查）

用戶手動跑 `0010_kiosk_realtime.sql` 報：`ERROR: 42601: syntax error at or near "not"` @ `alter publication supabase_realtime add table if not exists pos_orders;`。
**根因**：`ALTER PUBLICATION ... ADD TABLE` 喺 PostgreSQL / Supabase **唔支援 `IF NOT EXISTS`**（只有 `CREATE PUBLICATION` 支援），所以第 9 行 parse 失敗 → 成個 migration 喺 transaction 內 rollback，**乜都冇建到**：
- `pos_orders` / `pos_print_jobs` / `pos_soldout` 全部冇加落 `supabase_realtime` publication → anon realtime 收唔到 pos_orders 變更；
- `pos_orders anon read` 等 RLS policy 冇建 → anon client 根本讀唔到 pos_orders；
- `pos_soldout` 表冇建。
→ 呢個就係 POS 收銀秒級見唔到 kiosk 單（realtime 路徑）嘅真正原因；15s 輪詢係 service role 繞過 RLS 先有 fallback，但已經係「補短板」。

**修法**：`supabase/migrations/0010_kiosk_realtime.sql` 第 1) 段改成 idempotent DO block——先查 `pg_publication_tables`（`pubname='supabase_realtime' AND schemaname='public' AND tablename=t`）判斷，唔喺 publication 先 `execute format('alter publication supabase_realtime add table %I', t)`。`create table if not exists pos_soldout` / `drop policy if exists` / `create index if not exists` 本身語法 OK 唔使改。

**重要前提**：`pos_orders` 同 `pos_print_jobs` 必須已經存在（由 Macau-Ledger repo 嘅 migration 喺共用 Supabase 項目建立）先可以 `add table`，否則 DO block 內 execute 會彈 `relation does not exist`。跑之前確認 Ledger migration 已 apply、呢兩張表喺 `public` schema。

**影響**：呢個 migration 之前若用 `supabase db push` 跑過，失敗會 rollback 且 0010 唔會標記為 applied（重跑會再試）；若喺 SQL editor 手動跑就直接重跑修好嘅 SQL 即可。重跑成功後 realtime 路徑恢復，配合 Aug 22 嘅 15s 輪詢 + sync 硬化，② 應該解決。下一步 dev box build + push + 重跑 migration 驗證。

**第二次報錯 42P01（`relation "pos_soldout" does not exist` @ DO block line 13）**：我第一版 DO block 將 `add table` 排喺 `create table pos_soldout` **之前**，所以 `pos_soldout` 仲未建就想去 `add table` → execute 彈 `relation does not exist`，成個 block 中斷。**最終修法**：重排成 3 段——(1) `create table if not exists pos_soldout` + index 先；(2) DO block（加 3 張表落 publication，已有 `to_regclass('public.'||t) is not null` 守門，表唔存在就 skip，唔會硬掛）；(3) RLS enable + anon read policy + grant select。而家 `0010_kiosk_realtime.sql` 係呢個順序，可安全重跑。
