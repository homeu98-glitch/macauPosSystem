- `kind === "settlement"` 嘅分支（`ingest/route.ts` L249-263）**只寫 `pos_grabber_inbox` 就 `continue`**，
  註釋寫「投影 pos_orders 係之後嘅事（唔喺呢度硬做）」——但**冇任何地方做**：
  全 repo 冇 worker / trigger / route 讀 `inbox where kind='settlement'` 去 update `pos_orders`。
- `ingest` L278-280 解析咗 `business_amount_mop` / `gross_amount_mop` / `net_amount_mop`，
  但 **`gross` / `net` 之後完全冇用過**（`business` 只餵 `turnoverAmount`）。
- ⇒ `pos_orders.platform_net_amount` / `platform_subsidy_net` 嘅**唯一寫入者**係
  `/api/integration/grabber/settlement`（Chrome 插件路線）。
- 所以：若報表見到平台實收有數，嗰啲數**唔係 APK 寫嘅**；APK 送嘅對帳數只留在
  `pos_grabber_inbox.raw`（jsonb），報表完全讀唔到。

## ✅ 已修：實收金額被加總 2–3 次（真機 SQL 確診）

**證據**（J 提供 `pos_orders` 真實數據，store `8291f843…`）：
- 29 張已對帳：POS 營業額 2,641.00 / 平台實收 5,073.35（net 倍數 1.921）。
- 逐張拆：10-05 之後嘅單，金額**全部可以整除 3**（126 / 44 / 98 三張係整除 2）。
  除返之後比率穩定 0.73–0.80；9-25～9-30 嘅單（冇除）比率 0.45–0.78。
  ⇒ **同一筆錢喺同一批 payload 出現 2–3 次**，被 `groupSettlementByOrder` 加總。
- 例：`202610052011242327105` total 70.00 → 實收 165.90；÷3 = 55.30 = 0.790 × 70（正常 21% 抽成）。

**根因**：上游（抓取／插件）跨頁重疊去重漏咗，同一 tradeNo 同一金額送 2–3 次；
POS 側 `groupSettlementByOrder` 刻意「同一 tradeNo 多筆一律加總」（為拆單／退款），
所以重複投遞就變成幾倍，而且**有值但錯**（最難察覺）。

**修法**（POS 側，保護所有客戶端）：
- `groupSettlementByOrder` 加**完全重複去重**：簽名 = `tradeNo|net|subsidy|business|fee`
  全部欄位一樣才丟；`null` 同 `0` 分開寫。回傳新 `duplicateCount`（唔可以靜默丟）。
  真拆單金額必然唔同 ⇒ 照舊加總（測試覆蓋）。
- `settlement/route.ts`：`duplicateCount > 0` 出 `console.warn` + 回傳欄位。
- `MfoodTotals` / `SettlementTotals` 新增 `settledReceivable`（差額率真正分母）
  同 `overReceivable`（實收 > 應收 ⇒ 異常旗標）。

  唔再扮 `0.0%`；footer 分母改用 `settledReceivable`（之前印 `receivable` 對唔上）。
